Lea: what happened, start to finish

Lea is a small ruleset for Claude Code: 226 words (~180 tokens) read to the model when a session opens. Its purpose is to get the same work done on less quota.

This page tells the whole project in date order: where it started, what was measured, what was approved, what was dropped and what runs today. 16 August – 11 November 2026.

In short Three questions, three answers

What is Lea?

A single SessionStart hook. It tells the model: keep the explanation to 120 words, do not read the same file twice, do not repeat a check that passed; but if the code you are fixing states a contract, check every clause of it.

Not a plugin bundle, no dependencies. The setup it replaced loaded ~6,000 tokens of rules.

Does it work?

In the benchmark, yes: on Opus 26% – 51% cheaper than rivals measured the same day, at the same correctness. On the hard bug-fix test, version v8 raised v7's correctness from 4/20 to 13/20.

Measured again on 11 November with today's models: v8 is still cheaper than superpowers, but 4% – 10% dearer than Claude Code with nothing installed on short tool tasks.

The same day a pilot ran on real session openers: Lea is cheaper than full, the install it replaced, in 18 of 18 pairs (median ratio 0.44 – 0.48). Against a bare install there is no decision. The limits are in table 8.

The saving in real daily use could not be measured directly; the published figure is a projection. The chart is just below.

How do I install it?

claude plugin marketplace add hero-999-dev/project-lea-web
claude plugin install lea@lea

Restart Claude Code. If the first line of the session is LEA ACTIVE, it is loaded. Nothing else is installed: no telemetry, nothing written to disk.

Needs node. To remove it: claude plugin uninstall lea@lea

What exactly does Lea tell the model? (226 words) 
LEA ACTIVE - always on. Terse prose, unlimited analysis.

Prose budget: at most 120 words of explanation per reply, plus whatever code or data the answer
needs. No preamble, no restating the question, no closing summary, no "note that", no hedging, no
offer of further help. Lead with the answer. Fragments are fine. Bullets beat paragraphs.

Code: each implementation once, complete. Never re-paste unchanged code - name it, state the delta.
When you build a file or an artifact, none of this budget applies to the artifact itself: validation,
error handling and platform basics (a web page keeps its viewport meta, title, labelled controls)
survive every cut. Shorten the prose about the work, never the work.

Tool loop: read what the task needs, change it, check once, report. No re-running a passed check,
no re-reading a file already read, no narrating the call you are about to make. Turns are the bill.

One exception, and it overrides the budget: when the code you are fixing states a contract - a
docstring, a spec, a type - checking every clause of it against the implementation is required, not
optional, and your analysis there is unlimited. A green test suite is not that check; it is someone
else's sample of the contract. Say what you checked. Explaining a concept in chat is not this.

Everything else: 120 words.

What has it saved the developer? So far; a projection, not a measured saving

What Lea has saved the developer so far, at least $2,196 −26% in token value

Measured use, valued at API prices: $6,116.50 (711 prompts, 25,713 turns, 2026-08-30 → 2026-11-10). The same work under full, the setup that ran before Lea, would have come to $8,312. Upper bound $6,465 (−51%).

Lower bound: the measured round that favours Lea least (easy bug fix, n=3/3). A measured ratio × measured use — not a directly measured saving. These figures are not a bill: the CLI runs on a Claude Pro subscription, there is no API key, so no money leaves any account. What runs out is quota. The dollar is the common unit for comparing two setups: token counts valued with API price vectors derived from 205 measurement rows. Figures frozen on 11 November 2026.

How to read this figure:

  • The sum is: the measured cost of real use × the ratio measured in the benchmark. The worst ratio was used (26%); the best gives 51%.
  • What real use “would have cost without Lea” was never measured. Both rigs meant to measure it were retired without producing a decision.
  • The records were frozen on 11 November; the figure no longer grows, this is its final state.
  • In real sessions about half the cost goes on re-reading the conversation and only a fifth on output. The real lever is not a short reply but the number of turns and the length of the conversation carried.

Where it stands As of 11 November 2026: what is in force, what was dropped, what is pending

Approved  in force

  • The Lea v8 ruleset — live since 30 August; not a word has changed since.
  • The 200k compaction window (autoCompactWindow) — switched on 14 October; it held the bar written beforehand.
  • Distribution as a plugin — installed with two commands since 10 November.
  • The measurement rules — the rival is measured the same day, the bar is written before the round, a single measurement is not evidence.

Dropped  and why

  • The old 11-plugin setup — its cost was measured; it went down to 3, then Lea replaced it.
  • The v9 candidate — did not beat its same-day control (p = 0.35).
  • A new rule paragraph (v10) — the records held no measured waste for one to cut.
  • The shadow arm — 10 usable pairs out of 2,430 prompts; it produced no decision.
  • The daily Lea/stock flip — no visible difference, and no power to see one.
  • Early headlines — “full is cheapest, $2.90”, the quality ranking, v7's 4/5: all three fell when measured again.

Open  answer pending

  • The v11 read — synced plugins were switched off; the first check passed. The prediction was $0.10 per turn and the bar $0.13. The interim read on the evening of 11 November (639 of 2,000 turns) is $0.195: the prediction is not holding. Why: the base reloaded after every compaction is larger than expected.
  • v12: a trimmed base — same ruleset, same window; tool schemas and skill descriptions that are never called are no longer carried on every turn. Switched on 11 November on the development machine only, its bar written beforehand, its effect not yet read. Not in the downloadable plugin.
  • The saving in real use — still a projection. Both rigs meant to measure it were retired.
  • v8 beside a bare install — in the 11 November round the bar written beforehand held on three of eight tests: v8 is 4% – 10% dearer than a bare install on short tool tasks. What to do about it has not been decided.

Roadmap The next steps. The downloadable version does not change until an improvement is proven and tested.

Rule  the download is frozen

What the Lea you install as a plugin does to the model (the v8 ruleset) does not change without all three:

  1. The prediction and the bar are written before the trial.
  2. The bar held on the development machine — one reading is not evidence.
  3. The change was tried on a second, clean install.

This page keeps being updated after every round, including the results that did not hold.

12 November, 8.4.0: same ruleset. Only commands the user types were added (/lea: a status block; /lea full <question>: one reply without the word budget; /lea-guide: the guide). They do nothing unless typed; tried on four models. So that these names work, the plugin writes two files to your commands folder when a session starts, and adds nothing to what the model reads.

Next  step by step

  1. Read v12. The bar: the median carried after a compaction is 55k tokens or less in the terminal and 95k or less in the desktop app. Read once each has at least five compactions.
  2. If it holds, try it on a second install. The base trimmer is run on a clean install: does it report the right things, is its undo complete.
  3. If that passes too, add it to the plugin. As an optional command; the ruleset does not change. If it fails it is undone and listed here as dropped.
  4. The 4% – 10% gap on short tool tasks. A candidate is tried only in a round with a same-day control, 20 runs per arm.
  5. The new model's price. Once its price tier is known the dollar tables are recomputed; until then those rows stay marked.
  6. The saving in real use. A new measuring rig is built only if a power calculation shows it can produce a decision.

Period 1 · The question and the benchmark — 16–24 August

  1. 16 August 2026 · Event

    It all began with two faults

    Skills stopped loading on their own in Claude Code. The cause was two configuration errors, fixed in an afternoon. One question was left over: eleven plugins were switched on, and nobody could say what any of them cost or whether it helped.

    Outcome: the whole project is the answer to that question.

  2. 17 August · Approved

    Eleven plugins became three; the measurement rig was built

    First, what each plugin loads into a session was counted, and eight of the eleven went. Then a rig was written to measure benefit: five setups, the same tasks, graded by hidden tests the model cannot reach. The first four test rounds ran the same day.

    Outcome: no setup won everywhere. The short-output plugins were 45% cheaper on prose and up to 45% dearer on tool work; the setup with everything on nearly doubled on tool work.

  3. 18 August · Withdrawn

    The first headline: “the current setup is cheapest, $2.90”

    Each setup was given a copy of a real seven-language site and told to improve it. One run per setup, and the current setup came out cheapest.

    Outcome: at three runs the headline died: one setup's own runs ranged from $2.78 to $9.39.

  4. 19–24 August · Withdrawn

    The quality ranking could not be repeated

    The setups had differed in quality on one test only. A second trap task was written to repeat it: every setup passed. All rounds were run again on Opus: the quality gap vanished entirely.

    Outcome: “this setup hurts correctness” belonged to one day and one task; it was withdrawn. The direction of the cost differences held on both models.

Period 2 · Designing Lea — 25–30 August

  1. 25 August · Approved

    Instead of picking a setup, a new one was written: Lea v1 → v7

    The measurements had shown three mechanisms: on prose the saving comes from short output; on tool work the loss comes from a long ruleset re-read every turn; and correctness depends on output volume during the contract check. Lea was written to those three, and seven versions were tried in a day.

    Outcome: v7 was cheaper than the test's best rival on three of five tests and level on two. The founding rule was born the same day: a new run is never compared with a stored old figure.

  2. 26 August · Approved

    Opus confirmed it; Lea went live

    The same tests were measured on Opus with the rivals re-run the same day: 42% cheaper on prose, 53% cheaper on the hard bug fix at the same correctness. The daily setup was switched to Lea v7.

  3. 26 August · Withdrawn

    v7's “4/5 correct” did not repeat

    An unchanged v7 had scored 4/5 on the hard test the day before; the next day it scored 1/5, and three days later 2/14. Cost did not move; correctness did.

    Outcome: a quality figure resting on one day is not evidence. In every later comparison both sides ran the same day.

  4. 27–29 August · Event

    Three days in which nothing could be measured

    The runner hit a usage limit, could not read when it would lift, and slept blind for five hours; four times. Then the machine shut down.

    Outcome: the rig now probes at short intervals instead of guessing.

  5. 29 August · Approved

    The deciding round: v8 beat v7

    A failed v7 run was read: the model saw the visible tests green and closed the job with “all tests pass”. v8 changed a single paragraph: the contract check is no longer a permission, it is an obligation. Both versions ran twenty times each on the same day.

    Outcome: v7 4/20, v8 13/20 (p = 0.010); v8 was also 7% cheaper and 36% faster.

  6. 30 August · Approved

    The benchmark closed; the live setup moved to v8

    The last worry was measured too: is Lea dearer on a real project? It is not (median $3.74, the old setup $5.56). The power of that round was measured the same day: with so few runs it cannot prove any ranking. That v8 does not make prose dearer was confirmed as well.

    Outcome: 286 graded agent runs, 0 failed cells. Lea v8 has not changed since.

Period 3 · Attempts to measure real use — 30 August – 13 October

  1. 30 August – 2 September · Dropped (on 11 November)

    The shadow arm was built

    The idea: answer every real prompt a second time in the background with a setup without Lea, and put the two costs side by side. On the first day all 5 pairs collected under a loose criterion turned out not to be comparable; on 2 September the rig was found to miss exactly the prompts that open a session, and was fixed.

    Outcome: it ran for ten weeks and produced no decision; see 11 November.

  2. 4 September · Dropped

    A third hard task and a screening round

    A new hard task was written to screen v9 candidates; calibration showed it did not tell the versions apart. The planned screening round was calculated to lack the power to see the difference.

    Outcome: the task was not used, the screening round was not run.

  3. 5 September · Dropped

    v9 was tried and did not pass

    A v9 candidate was measured against a v8 control run the same day: candidate 36/40, control 32/40, p = 0.35. The bar had been written before the round and was not cleared. The round's real finding was something else: v8's “13/20” was not a rate. The same version scored 13, 15 and 17 in three blocks; the real rate is 45/60 = 75%.

    Outcome: there is no v9. Measured against the old 13/20 the candidate would have read as a win; the difference came from the day, not the arm.

  4. Night of 5 September · Dropped (on 11 November)

    The daily Lea / stock flip began

    The second route: work one day with Lea, one day without, and compare the days. It cost nothing extra, but half the days ran without Lea, and seeing a 25% difference needed 518 records per arm.

  5. 6 September · Event

    The source repository went private; the site moved to a separate copy

    Since that day this site lives in a separate, public repository: the report pages, the install guides and the source zip.

  6. 29 September · Event

    Shadow runs touched real files

    The background replays worked with real tools and raced a project's live files. The runs were fenced into separate working copies.

  7. 13 October · Withdrawn

    The “Lea is 2.5× dearer” table was not a comparison

    The raw table of the daily flip showed Lea 2.5 times dearer per prompt. The two sides were not the same population: Lea days had more Opus and far longer sessions. Looked at with the same model and the same session depth, the ratio came out at 0.95.

    Outcome: no visible difference; this rig could not have seen any difference under 2×.

Period 4 · A setting, not a paragraph — 14 October – 11 November

  1. 14 October · Dropped

    A new paragraph was looked for in v10, and not found

    The recorded sessions were read turn by turn. The waste a rule paragraph could cut was already small: look-only turns that could have been batched 2.6%, repeated reads 4.2%, median reply 122 words.

    Outcome: no v10 for the ruleset; the v8 text stayed as it was.

  2. 14 October · Approved

    The money was not in the rule but in the re-read conversation: the 200k window

    What a turn costs is set by the conversation it carries, and Claude Code let a conversation grow to 1M tokens. One setting (autoCompactWindow: 200000) has the conversation summarised at 200k. The prediction and the bar were written before it went on: from $0.256 per turn to $0.146; $0.19 or less holds.

    Outcome (read on 10 November): $0.170 over 9,021 turns. The bar held, the prediction did not. The harm gauges stayed under their limits.

  3. 10 November · Approved

    Lea became a plugin

    Lea is now a Claude Code plugin installed with two commands: a single hook carrying the ruleset and nothing else. The measurement rig is not handed to users; development happens in one place.

  4. 10–11 November · Open

    v11: the same ruleset, a lighter session start

    Why the prediction missed was looked for: the session's starting load had grown (62k tokens in October, 89k in November) and was eating the 200k window. One layer of that load was the plugins and connectors synced from the account; the sync was switched off.

    For now: the first check passed (the first session carried 51k, the bar was 60k). The real read comes after 2,000 turns, counted on the development machine only: 216 on 11 November.

  5. 11 November · Dropped

    The shadow arm and the daily flip were retired

    The shadow arm: 2,430 prompts recorded, 78 ran, 10 usable pairs, $54 spent. Worse, the gap between the pairs measured the two sides' different starting load, not Lea. The daily flip: ratio 0.71, p = 0.42; no visible difference.

    Outcome: both were dismantled, their records frozen, and they will not be rebuilt. The package handed to users contains no measurement rig.

  6. 11 November · Open

    v8 beside each test's best rival, the same night

    Until then v8 had been measured only on Sonnet, on the hard test and on plain text; the other figures were v7's. On eight tests v8 and that test's best rival ran the same night, arms alternating, five runs each: 80 runs, $7.65. The bar was written before the round: on no test is v8 dearer or less correct than the rival.

    Outcome: the bar held on three of eight tests. v8 is cheaper than superpowers; against a bare install it is 4% – 10% dearer on the four tool tests. No difference in correctness: all 80 runs passed, so the tests no longer separate today's models. What to do about it is open.

  7. 11 November · Open

    A pilot on real session openers

    The benchmark measures fixed tests; real work had not been measured. Nine questions that opened the developer's own sessions ran headless the same morning, arms alternating: two blocks, 45 runs, $8.31. The fence was built first: the session holds read-only tools, the working folder is a copy, a read outside the copy is refused, no connector is loaded; nothing was written and the copies were removed. The reading rule was written before the second block.

    Outcome: Lea is cheaper than full in 18 of 18 pairs (median ratio 0.44 and 0.48). Against a bare install it is cheaper in seven of nine pairs, median 0.87, but p = 0.105 and the dearest job went the other way: no decision. The answers were not graded; the savings figure did not change.

Lessons learned The numbers changed; these rules are what stood

  • Measure the rival the same day. Do not compare with a stored old figure: the same setup gives a different result on a different day. v9 would have looked like a win against the old figure.
  • One measurement is a hypothesis, not evidence. The $2.90 headline, 4/5 and 13/20: each was a single draw.
  • Write the bar before the round runs. A threshold set after seeing the result always holds.
  • Work out what a rig can see. The project round, the shadow arm and the daily flip did not have the power to see a difference of the size they were looking for.
  • A full score can hide a defect. All three sites that scored 7/7 on the web test lacked the mobile viewport tag; the test measured behaviour, not appearance.
  • In a rule text, position matters more than content. Every sentence added in the middle diluted the word budget; the same sentence shortened, with the budget moved to the end, brought the result back. Four times.
